# Архитектура AmeOS

## Границы системы

1. **База FreeBSD:** ядро, драйверы, libc, системные утилиты, rc и установщик.
   Исходная иерархия остаётся на месте, чтобы облегчить получение исправлений.
2. **Интеграция AmeOS:** профили, сборка образов, будущие настройки системы
   и пакеты. Этот код находится в `ameos/`.
3. **AmeDE:** пользовательская сессия и компоненты окружения. Они должны
   устанавливаться пакетами в `/usr/local`, независимо от базовой системы.
4. **Оформление:** общая палитра и ресурсы для компонентов AmeDE и приложений.

На первом этапе реализуется только механизм сборки базы. Проект не объявляет
готовыми рабочий стол, установку AmeDE или обновления.

## Решения первой итерации

- **База:** сохранить существующий коммит FreeBSD 16.0-CURRENT
  `0a12444b2989c38a5d2e358e0f9ef01c665cc268`. Миграция на RELEASE — отдельное
  решение до публичных сборок с учётом графики и пакетов.
- **Первая цель:** amd64, GENERIC, консольные ISO и USB-носитель.
- **Сборка:** чистый Git-коммит архивируется в новый каталог; штатные
  `buildworld`, `buildkernel` и release Makefile работают с отдельным objdir.
  Источники не скачиваются повторно с изменяемой ветки `main`.
- **Пакеты:** внешние пакеты, ports и pkgbase отключены в начальном профиле.
  Следующий профиль должен фиксировать репозиторий, версии, подписи и ABI.
- **Совместимость:** сохранить `uname`, ELF ABI, `__FreeBSD_version` и
  техническую нумерацию FreeBSD. Сведения о продукте и версия AmeOS должны
  развиваться отдельно от версии ядра.
- **Проверяемость:** каждая сборка сохраняет коммит, базовую ревизию, настройки,
  сведения о хосте, логи и контрольные суммы образов. Это ещё не доказательство
  побитовой воспроизводимости на разных хостах.

## Прототип AmeDE

Первый прототип следует построить поверх готового композитора. Wayfire —
кандидат, а окончательный выбор зависит от запуска на выбранной базе и GPU.
Собственный композитор не входит в первый прототип.

Сессия должна запускать панель, док и сервис уведомлений, обеспечивать выход,
блокировку и быстрый запуск готового терминала. Компоненты не должны требовать
root для обычной работы. Привилегированные настройки системы получат отдельный
минимальный интерфейс с проверкой прав.

Для первой аппаратной проверки нужны матрица GPU/драйвер/версия ядра,
тест клавиатуры и мыши, звук, несколько мониторов и приостановка работы.
Поддержка железа не выводится из успешного запуска в VM.

Справочник: [Wayland в FreeBSD Handbook](https://docs.freebsd.org/en/books/handbook/wayland/).

## Обновление upstream

Для обновления базы нужен отдельный change: новая ревизия, просмотр `UPDATING`,
слияние изменений, полная сборка и загрузочная проверка. Затем обновляется
`base-revision`. Скрипт проверяет, что эта ревизия есть в истории HEAD;
проверка происхождения коммита из официального upstream остаётся задачей review.

Коммиты AmeOS должны быть небольшими и отделять изменения базы от окружения.
Обновления установленной системы и откат ZFS boot environments будут
проектироваться отдельно; начальный скрипт их не реализует.
